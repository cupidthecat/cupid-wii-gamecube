These observations were recorded on 2026-10-04. The game captures are raw guest fields, so their pixel aspect differs from the timing-derived shape used by the current output window. They establish visible startup only. Sunshine's matched three-billion-instruction Windows and Linux runs have identical full final JSON states, PCM hashes, and raw field bytes. The PPM SHA256 is `869f0528f7ef85ee3cca9abddc72027c0a6c23a1afd215b7d7e88254cc723a17`. Galaxy's latest runs have different bounds and input conditions and are not a full cross-platform state comparison.

Sunshine's startup sweeps address ranges much larger than physical RAM for cache maintenance. The first sweep returns at about 209 million guest instructions. Increasing a development bound to reach its return preserves guest execution; no game-specific skip was added.

The first longer Sunshine run stopped on an unimplemented locked-cache DMA register at 2,087,239,936 instructions. The physical transfer and register rules now have focused regressions, and the matched three-billion-instruction run passes that point. Its intro card is a startup observation, not an interactive title-screen result.

The three local IPL candidates each have the expected 2 MiB size, but none matches a recognized full-ROM checksum. They have not been accepted as full firmware. The USA container's font slots pass bounded decompression and glyph-layout validation and supply the EXI font reads used in Sunshine's startup. This does not authenticate its boot-ROM bytes. See [font validation](fonts.md).

The host CPU is an Intel Core i9-10900F with 10 cores and 20 logical processors. The Windows Galaxy 492,998,315-instruction probe took 78.488 seconds while other validation work was active. That is a bounded startup measurement, not a gameplay benchmark. Future performance records should include active concurrent work and the guest video/audio rate.

## Recording a new result

Record the source revision and working-tree status, platform/compiler, graphics and audio backend, console, input mapping, user-data conditions, run bounds, final state, and visible behavior. Keep private traces local.

Use separate milestones: apploader completed, title screen reached, gameplay reached, and playable. Playable requires rendered gameplay, usable controls, audio, and demonstrated save/load behavior. A frame count or successful bounded exit alone is insufficient. Sanitizer, package, and helper comparisons validate their named paths; they do not establish a game's playability.
