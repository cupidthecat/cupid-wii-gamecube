# Device behavior and verification

The device module uses physical addresses and big endian register values. It runs on the same CPU cycle counter as the interpreter. GameCube uses 486 MHz; Wii uses 729 MHz. Unsupported MMIO accesses raise a bus fault with the address and access direction.

Device advances update the public cycle counter and timed level interrupts on every call. Calls strictly before the next timer deadline accumulate event-free elapsed time; MMIO access materializes it, and a write invalidates the deadline. Audio DMA, AI sample clocks, VI half-lines, disc completion, ARAM completion and both memory-card timers all participate. At a boundary, earlier elapsed time is applied before the current call so a throwing callback retains the original partial-update order. Reentrant register callbacks and zero-cycle interrupt reassertion are covered.

A private comparison with the preceding device implementation checked 263,146 instruction advances and 1,112 complete state snapshots on both consoles, including DMA data, callback order and cycles, rate changes, card completion, reentrant access and thrown callbacks. Six alternating unprofiled GCC Release runs of the same 100-million-instruction headless startup produced identical complete state dumps. Their median times were 9.19 and 6.42 seconds under concurrent work; this is a bounded startup measurement, not a general game-speed estimate. Both complete runtime versions passed the device, IOS, runtime, graphics, SDP transport and EFB access suites.

The behavioral reference is pinned to commit `562875dd60fd0ff50b65dbbb611a2096802cd1b9`. The implementation was written in this project's register and callback model. Paths below are relative to the behavioral reference checkout.

`tests/device_tests.cpp` exercises the public device API with synthetic RAM, disc and controller inputs. These are behavioral regression checks derived from inspected register operations. They are not a differential execution run or observations from physical hardware. The test executable has been compiled with GCC and run on Windows.

A private interpreter check executed a supplied guest's `PADRead` routine with fourteen authored button states and its complete input caller with nine press, hold and release transitions. The returned status and port-zero input object retained the expected buttons and edges with no controller error. This checks that captured SDK path; it does not establish save-menu acceptance or general gameplay. The normal card observer separately compared 96 completed DMA reads, totaling 49,152 bytes, with the preserved raw card image. These commercial-game execution artifacts remain outside the product fixtures.

Audio, AI and VI period accounting avoids division when an increment cannot reach the next boundary. Exact-boundary and larger increments retain the previous quotient/remainder calculation, including phase carried across rate changes. The preceding period-only implementation still performed countdowns and interrupt updates on every `advance` call. Public tests compare the previous arithmetic across periods, split and bulk increments, unsigned limits and 10,000 deterministic rate changes. A private comparison of the previous and current whole-device implementations passed 48,336 register and callback checks for each console. Three isolated 20-million-call GCC benchmarks on Windows measured 2.06â€“2.13 times faster device calls; these measurements do not establish whole-game speed.

DI data reads currently complete after the reference's 300 microsecond minimum command latency. Seek position, read buffers, media transfer rate and per-sector scheduling are unfinished, so read timing does not yet match the full drive model. Read errors leave DMA address and length intact. Unsupported seek and disc audio commands stop execution with a clear diagnostic.

DSP mailbox and control accesses forward to the connected DSP runtime while this device module retains interrupt status and masks. When no runtime is connected, mailbox access and unhalting stop execution. ARAM DMA and audio DMA operate independently of that runtime. Wii ARAM DMA accesses the actual MEM2 backing through RAM callbacks. Wii IPC MMIO forwards to runtime service callbacks and faults if those callbacks are absent.

GameCube ARAM transfers whose starting address is outside the built-in 16 MiB reach an unattached high-speed port. Writes are discarded, and reads preserve the destination MRAM bytes. Transfers retain the same address advancement, busy state and completion interrupt. A private native trace established a 32-byte guest probe from MRAM `0x00427600` to ARAM `0x01000000`; its exact halfword instruction reproduced the failure before the regression passed. Checks also cover the 64 MiB address mirror and unchanged built-in ARAM. Expansion accessories are not attached or allocated.

SRAM can be loaded and saved through a 68-byte image. RTC uses an explicit epoch plus elapsed emulated seconds. The caller supplies a decoded 2 MiB IPL image. Font and peripheral reads fail when the needed image or implemented peripheral is unavailable.

UART and EUART collect the guest's original text bytes and deliver a line on carriage return. The callback receives the original encoding. These FIFOs report zero queued bytes because delivery is immediate. Initialization and unused offsets within the documented peripheral ranges retain their byte input. Accesses outside implemented peripheral ranges stop with the latched IPL address.

EXI keeps the guest's DMA address register unchanged and removes its two alias bits when calling the RAM transfer callback. A regression first reproduced the rejected Wii transfer from `0x80650820`, then verified the 64 SRAM bytes arriving at physical address `0x00650820`. A separate check covers an uncached MEM2 alias and preserves the low address bits.

DI retains Wii DMA address aliases in its register and transfer callback. The connected RAM span resolves the two top alias bits while keeping physical CPU accesses separate. A regression uses all four aliases for GameCube MEM1 and Wii MEM1/MEM2, verifies actual copied bytes and retained register advancement, and checks completion. The previous strict host span failed the six Wii aliases; normalization at the memory callback resolves them without changing DI register semantics.

Wii MMIO at `0x0d80xxxx` mirrors `0x0d00xxxx`. These windows expose IPC, DI, SI, EXI and AI; other register blocks retain their original physical locations. A CPU-level regression reproduced the faulting load at `0xcd800180` before verifying the zero register value and normal instruction advancement. A separate regression reproduced a 32-byte Wii ARAM DMA from MEM1 address `0x01000000` to MEM2 offset zero before checking real bytes, register advancement and completion timing.

Memory card slots start empty. The runtime can attach a raw card image or create a correctly formatted empty card of 4 through 256 Mbit. The formatter writes the header, two empty directories, two allocation maps and their checksums. Card writes and erasures mark an image dirty; the runtime saves snapshots in the explicit user-data directory. Games own the save-file contents and allocation updates. Unsupported card commands stop execution. The implemented DMA transfer rates are 512 KiB/s for reads and 98,432 bytes/s for writes; command completion is deferred by 5,000 CPU cycles.

VI presentation sends the field's XFB address, width, height, byte stride and active-area aspect ratio to the rendering callback. Aspect uses programmed blanking, nominal sample duration and even-field duration with the pinned NTSC/PAL normalizations; invalid timing retains its 4:3 fallback. Raw field pixels need this separate display ratio because they usually hold only one field's active lines. VI does not render GX commands or alter the guest image. Register changes during a scanout are not yet collated into a per-line display model.

`tests/ios_tests.cpp` verifies IPC and IOS services with synthetic guest requests and real temporary files. Wii storage is confined to `wii` under the explicit user-data directory. The runtime records node ownership, modes, attributes and creation order in `wii-fs-metadata.txt` beside that directory; its format starts with `CFS1`. The guest's UID is assigned through the real big endian `/sys/uid.sys` record format, and its group comes from the active TMD. Metadata changes persist through file replacement, and reconstruction tests verify the retained UID, group, attributes and access modes.

Filesystem usage accepts one 64-byte path vector and two four-byte output vectors. Each ordinary file contributes its size rounded up to 16 KiB clusters; directories contribute only inodes, including the queried directory itself. Returned totals are capped at the defined filesystem geometry: `0x7bc0` clusters and `0x17ff` inodes. The query intentionally does not check caller UID or GID, matching its specified operation. Host-only root files, invalid host names and symlinks remain outside the guarded guest namespace. Missing or invalid paths and malformed vectors retain the output bytes; an incomplete host scan returns an access error rather than a partial count.

An independent build of the unchanged filesystem backend, directory scanner and file utilities matched 5,006 guest-request checkpoints and 60,072 result bytes. It covered 128 seeded directory trees, per-file cluster boundaries, nested inode counts, both caps, root counts, and missing or ordinary-file errors with unchanged output buffers. Guarded namespace exclusions and the explicit incomplete-scan error policy were outside this comparison.

Ordinary file paths and `/dev/fs` share the filesystem service. Their valid descriptors can issue the implemented filesystem ioctls; individual operations retain their own UID/GID checks. Regression requests through a read-only ordinary file descriptor verify NAND statistics, directory usage and unchanged file position, then verify that closing the descriptor restores the invalid-handle error without touching output bytes.

NAND statistics return seven big endian words in at least 28 output bytes: 16 KiB cluster size, free and used clusters, zero bad clusters, `0x300` reserved clusters, and free and used inodes. These values describe the defined host filesystem profile, using the same actual root-file counts and caps as directory usage. Bytes beyond the seven words remain untouched. Valid replies use the normal 48,000-cycle IPC delay; malformed output sizes use the 32,400-cycle filesystem error delay. An independent build of the unchanged NAND statistics backend matched 2,170 guest-request checkpoints and 69,440 result bytes across the seeded trees and both caps, including unchanged trailing output bytes. This backend comparison does not check timing; separate IPC regressions check both reply boundaries.

Title context accepts structurally valid, matching disc ticket and TMD bytes; it does not authenticate their cryptographic signatures. The selected disc TMD and data directory are persisted, while a disc ticket is not reported as an installed ticket. Installed-title queries enumerate actual storage directories. Content queries require the actual ordinary content file or the matching shared-content map entry and file. Caller-supplied partition credentials, title launching, device credentials, storage formatting, quota queries and other unfinished services stop with an explicit diagnostic.

The IOS tests can take private ticket and TMD file paths plus a partition offset. This path was run against the supplied Wii disc's original metadata at partition offset `0x0f800000`: it checked the title ID, raw TMD size and bytes, exact ticket-view bytes, ticket consumption, rejection before opening a partition and successful opening with the selected metadata. These checks establish metadata and IPC behavior; they do not establish game playability or signature authentication.

An ES consumption query must match a selected or installed ticket ID. Eight disabled limit records establish an empty consumption list; the count response is zero and the limits buffer remains untouched. Tickets with enabled limits stop explicitly until persistent consumption tracking exists.

STM event hooks remain pending until the caller delivers a reset or power button event. Idle and shutdown require a connected host shutdown handler. The implemented hot-reset, video-dimming and LED-mode requests retain their specified no-effect behavior. DDR queries and other unfinished STM operations stop explicitly.

Host Wii input uses explicit 10-bit acceleration and infrared object coordinates. A linked Remote emits HID reports; an unlinked Remote emits none. Nunchuk attachment changes emit status and disable data reports until the guest chooses a mode. EEPROM supports its real usable 5,888-byte range, factory calibration and caller-loaded images. Memory reads use 16-byte replies and report real address-space, missing-peripheral and busy errors. First-party Nunchuk register reads and input reports support the selected extension key. Relinking or attaching a Nunchuk resets its configuration and restores calibration; EEPROM contents remain intact.

Full infrared objects use nine bytes each, preserving the reference's seven-bit bound truncation before intensity calculation. Reports `0x3e` and `0x3f` alternate 18-byte halves of this 36-byte data, with their specified X/Y and split Z acceleration bits. Only a data report advances the phase; memory reads and status replies do not. An independent build of the unchanged camera and report implementations passed 55,128 checkpoints and 1,812,576 compared bytes on both GCC and MSVC, covering coordinate and size boundaries, tracking states and every 10-bit acceleration value on each axis. Those comparisons supply projected coordinates; camera projection is outside their scope.

Nunchuk key records occupy registers `0x40` through `0x4f`. Overlapping writes mark the derived key dirty; the next read with encryption register `0xf0` set to `0xaa` regenerates it. Seven first-party profiles and the defined fallback cover key selection. Raw writes remain unencrypted. Input reports use the same encrypted register read at address zero. Relinking or attaching the extension clears its key and marks it dirty.

Read replies keep the full 16-bit requested address while the bus uses its low byte. For a partial encrypted read at the register-bank end, the pinned implementation encrypts the whole requested span, including its unread zero suffix, then reports NACK. Tests preserve that behavior. The caller also retains its last accepted read slave: its I2C write guard tests that retained value for EEPROM address `0x50`, rather than the write slave. Authored tests reproduce the resulting errors, their persistence after a zero-length read and clearing on relink. Camera, speaker and extension banks all preserve the transferred prefix on a boundary error.

The actual Wii calibration request at offset `0x20` for 32 bytes first reproduced an unsupported-path failure in an authored local fixture. It now returns both encrypted 16-byte replies through HID and through guest USB/ACL requests. Expected bytes use independently checked zero-key and phase-varying key vectors. These tests establish protocol behavior; later game execution still requires its own integration run.

The Remote speaker has a 256-byte register bank at I2C address `0x51`. Register reads and writes retain a transferred prefix when a request crosses the bank boundary, then report NACK. Format, little endian sample divisor and volume feed a stateful PCM8 or Yamaha ADPCM decoder. HID sample reports honor the mute flag; direct I2C sample writes bypass it. A link reset clears registers and decoder history.

Host speaker processing defaults to disabled, matching the pinned setting. HID speaker-enable changes only the guest-visible status bit. When a caller enables processing, decoded mono samples are delivered through a separate typed callback with the exact 108 MHz rate divisor and left/right gain values. Enabling processing without an output callback stops explicitly. With host audio enabled, the runtime routes these packets through four separate speaker queues and mixes them with the main DMA queue. Speaker samples remain separate from main AI DMA telemetry. Public tests cover the disabled default and an enabled callback through guest USB/ACL requests. The end-to-end Machine fixture uses ordinary CPU instructions and public memory/MMIO interfaces to negotiate channels, configure the speaker and deliver PCM on all four Remote ports; it also checks the distinct host/HID enable controls and unchanged main DMA counters and hash. Separate backend tests cover mixing and channel routing. An independent build of the pinned speaker decoder matched 26,112 checkpoints and 397,658 mono sample values, including decoder state and rate/gain metadata.

Acceleration packing retains the pinned reference's low-bit behavior: X contributes two low bits and Y contributes one; the Z low bit is dropped by its two-bit assignment. The packet regression exercises a Z value with that bit set. An independent build of the reference's `DataReport.cpp` builder passed 27,648 comparisons against this implementation across nine noninterleaved report layouts, covering all 1,024 raw values on each acceleration axis with varied button bits, disabled infrared and absent extension payloads. The standalone helper lives in the ignored validation directory.

Bluetooth controller query and configuration responses use its defined device profile. The profile registers four Remote identities and an inactive board identity. Read-all link-key queries return their five generated protocol keys in an event before command completion; these keys do not come from private console credentials. Delete requests for a known peer report zero keys removed, retaining the preset profile exactly as the pinned behavior. Tests re-query the keys to verify that retention. Host input still exposes four Remote ports, and board input remains unavailable. Single-address key queries and mutable pairing-key storage stop explicitly.

`CommandLinkKeyRep` and `CommandLinkKeyNegRep` complete with status and the supplied peer address. They retain the preset profile; a key reply does not install private credentials or establish authenticated pairing. Authored reply packets and the later unchanged key query are checked.

Inquiry immediately reports the first available unlinked host peer and completes with the profile's two-byte status/count payload. Reset retains the pinned profile's no-effect behavior, including scan settings and established links. A rejected acceptance reports a connection timeout without a successful role-change event. USB interrupt and bulk requests remain pending until their respective packets exist. A host-connected Remote can establish an HCI link, negotiate real L2CAP CIDs, MTU and configuration, and deliver HID input over ACL. A guest IPC regression runs this path through exact discovery packets, input and rumble changes, and a host disconnect event. Unfinished controller commands and protocol options remain explicit unsupported paths.

USB close resets scan state, packet counts and pending endpoints while retaining links, channels, settings and queued packets, matching `Bluetooth/BTEmu.cpp`'s `Close`. Reopening cancels stale update schedules instead of creating duplicate controller ticks. The regression preserves a queued controller event across close, queries the retained link, receives HID data on its existing CID and then observes the host disconnect. `CommandChangeConPacketType` emits command status followed by the packet-type change event for a registered peer; the exact captured handle `0x0100` and type `0xcc18` are checked. Its target event behavior does not change virtual ACL packet geometry.

Disconnects restart the 200-update reconnect delay at the controller's 200 Hz input rate. After that delay, an inactive available peer requests a connection only when buttons are pressed. Initial host attachment can request its first connection immediately when page scan permits it. Regressions check held input at the 199th and 200th updates, delayed fresh input, unavailable peers and an already inactive disconnect. A repeated L2CAP PSM receives the defined no-resources result `3` without replacing its existing channel.

Wii storage initialization updates `/shared2/sys/SYSCONF` before guest file access. `BT.DINF` contains the five registered and active profile records with reversed Bluetooth addresses and protocol names; the board remains an inactive input source. A missing file receives the defined defaults and the nickname `Cupid`. New configuration nodes use system-menu UID `0x1000`, GID `1` and read/write modes for each access class. A valid existing file retains unrelated entries and settings, with its first prior image preserved once as `wii-sysconf-backup.bin` beside the Wii directory. Existing malformed or unreadable files stop initialization; unsafe destination and temporary-file paths are rejected. An independent build of the pinned configuration parser and serializer matched 129 complete files, or 2,113,536 bytes, covering defaults, authored settings and a supplied game's earlier configuration. The source serializer's 256-byte small-array defect is excluded from that comparison; a separate public test verifies preservation of that format-valid boundary.

`CommandWriteLinkPolicy` emits its defined command-status event. `CommandSniffMode` follows status with a mode-change event containing the requested maximum interval, and `CommandWriteLinkSupervisionTimeout` completes with the supplied handle. Authored packet regressions check their exact replies. These target handlers do not change virtual transport scheduling or introduce a radio timeout.

`CommandSetEventFilter` completes without applying a filter, following its specified behavior for the immediate inquiry profile. Packet checks cover an inquiry filter and clearing filters. This named compatibility response does not enable unsupported controller commands.

Named vendor commands `0xfc4f` and `0xfc4c` follow `Bluetooth/BTEmu.cpp`'s `CommandVendorSpecific_FC4F` and `CommandVendorSpecific_FC4C`: they acknowledge valid HCI framing without changing the controller profile. The exact four-byte clear request `4f fc 01 00` and six-byte completion are checked. An authored 187-byte upload packet checks its completion and retained guest bytes. The virtual transport ignores chip patch content as a deliberate target behavior; it does not execute firmware. Private game patch bytes are not included in public fixtures. Unknown vendor commands remain unsupported, with a separate regression checking that rejection.

The runtime can install separately validated compressed font bytes in the two bounded IPL font slots. Outside those supplied bytes, reads still require the full ROM and report the requested byte address. Font DMA tests verify both slots, reject empty or oversized inputs, and preserve failures for missing boot-ROM bytes. Installing a full decoded ROM replaces the partial font slots.
