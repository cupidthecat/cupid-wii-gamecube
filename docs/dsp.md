# DSP tasks and audio

The DSP engine handles the boot ROM mailbox protocol, initialization, CARD, the DAC audio task family and the standalone handheld authentication task. The runtime connects its mailbox and control registers through the device bus. The device layer keeps DMA status, interrupt masks and interrupt acknowledgments.

CPU mailbox writes become a complete message when the low half is written. The busy bit clears after the engine handles that message. DSP mailbox reads return the pending message's high half without consuming it; reading its low half consumes the message and clears the ready bit. A halted DSP keeps its previous readable message and leaves pending messages queued.

Reset starts the boot ROM protocol. Clearing the initialization bit starts the initialization task, which replies with its boot acknowledgment. The initialization-code bit clears after 130 time-base ticks. Task updates use the console's CPU clock and a one-millisecond interval.

Short instruction intervals accumulate without a division; crossing an update boundary retains the modulo phase and existing task notification behavior. Both implementations pass the same full DSP suite, and independently linked component and guest-startup comparisons retain their observable state. [Performance measurements](performance.md) records the measured scope and its limits.

ROM uploads record the source address, byte length, instruction-memory address, data length and entry point. The engine identifies the uploaded task from a computed hash of its bytes. CARD uses its mailbox completion and return-to-ROM behavior; it does not generate audio.

The audio task accepts setup, frame rendering, voice synchronization and task-switch messages. Setup reads coefficient tables and parameter-block addresses from guest RAM. Rendering waits for the CPU's voice masks, mixes eighty samples per channel and writes signed big-endian samples into the guest's left and right buffers. The guest interleaves those buffers and starts audio DMA. Host audio receives the bytes read by that DMA.

The mixer supports PCM8, PCM16, AFC with four-bit or two-bit sample codes, main-memory PCM streaming, square and saw waves, and supplied waveform patterns. It uses guest resampling and AFC coefficients, maintains decoder history and loop state, and writes back the mutable part of each voice block. Mixing includes volume ramps, positional volumes, low-pass and biquad filters, and four reverb rings. Wii audio reads the main-memory region selected by its base-address command; GameCube audio reads the same ARAM storage used by the device DMA engine.

Both ordinary and light mailbox protocols are implemented, including the smaller voice-block layout and explicit volume steps used by one boot firmware variant. Persistent audio state can be suspended for another task and resumed through the task protocol. Combined render commands consume their two reserved arguments without applying an additional effect, matching the behavioral reference.

The optional sample-history request count in a voice block is retained while ordinary decoding, mixing and mutable voice-state writes proceed. The behavioral reference leaves that requested history retention unmodeled in this profile. This is a deliberate compatibility behavior: no sample-history transfer is performed or claimed.

The known audio profiles retain optional variable-FIR parameters and history without applying that filter, matching the behavioral reference. Their ordinary low-pass, biquad, decoding and mixing paths still run. The named command `0x0d` consumes its one parameter where required and acknowledges it without an additional audio effect. Profiles that define it as a NOP consume no parameter. These are scoped compatibility behaviors; they do not implement variable-FIR processing or the unknown underlying command effect.

The two light audio profiles that define command `0x0c` as a JoyBoot authentication request consume its address parameter and compute the key and authentication word in guest RAM. The challenge uses little-endian byte order; the palette, interpolation speed, program length and destination use big-endian words. The result includes the padded-header length, eight-byte packet pairs and encoded palette parameters. An authored PowerPC guest exercises the command through the DSP mailbox registers and reads the computed result.

Profiles `0x24b22038` and `0x42f64ac4` define a separate two-word `0x0c` compatibility path. It consumes both reserved arguments before acknowledging the command and leaves guest RAM and renderer state unchanged. Their underlying operation remains unknown and unmodeled, matching the behavioral reference. An authored PowerPC guest verifies the two-word boundary, acknowledgment, unchanged RAM and subsequent command parsing through the mailbox registers.

The standalone task selected by hash `0xdd7e72d5` implements that authentication through its own mailbox protocol. Initialization queues its status word. The exact request word `0xabba0000` arms an address read; the task masks that address to 28 bits, writes the result and queues completion. Its one-millisecond update requests an interrupt while mail is pending. Exact reset and new-task controls are accepted after completion; unrelated words in those waiting states have the behavioral reference's defined no-effect handling. A new task consumes a ten-word upload descriptor and hashes the checked instruction bytes before switching.

Task switches retain the first suspended audio or standalone task. Returning to audio preserves its renderer state and deferred resume notification. Returning to the standalone task preserves its completed mailbox state, without restarting authentication or inventing a resume notification. Authored guest tests exercise DSP register writes and result reads, interrupt boundaries and both directions of task return on both consoles.

Unknown task hashes fail with the computed hash and upload descriptor. A general DSP instruction interpreter remains unfinished. JoyBus program transfer, a physical handheld connection and DSP save-state serialization are not implemented by these task protocols. Task switches that request DSP data-memory transfers also fail explicitly. Main-memory PCM requests that outlast their remaining sample count are rejected because the behavioral reference's terminal-padding branch leaves part of the sample buffer undefined. These limitations can stop software that requests them; they are not replaced by silence or a completion acknowledgment.

The public DSP tests use synthetic byte sequences and mailbox transactions. They check halting, read consumption, queued interrupts, reset, initialization timing, upload parsing, CARD dispatch, supported audio decoding, voice-state changes, synchronization, task resume and malformed requests. An original guest program interleaves decoded PCM and programs audio DMA; the test checks the samples delivered through the device callback. The synthetic task fixture contains no console firmware. Differential results and source mappings are in [DSP behavioral reference](dsp-reference.md).
